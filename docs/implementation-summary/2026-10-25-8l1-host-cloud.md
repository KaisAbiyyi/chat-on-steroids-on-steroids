# 8L1-HOST — source-owned Windows WebView2 host integration (cloud candidate)

Task: [#114](https://github.com/KaisAbiyyi/chat-on-steroids-on-steroids/issues/114). Branch: work/8l1-host-native-webview2-20261025. Environment: GitHub cloud exclusively. Source prerequisite: accepted 8B (profile/partition), 8C (lifecycle/permissions), 7L2 (authenticated Rust/MV3 bridge).

## Bounded implementation

- New apps/windows-host product-owned build target links the already native-tested 7L2 WinForms, WebView2, CDP and authenticated MV3→Rust bridge sources rather than renaming or replacing the synthetic probe binary.
- Native8L1Authority exclusively receives actual browser-owned CoreWebView2 profile path, tab, worker, document, channel and generation from WebView2/7L2; creates bounded opaque per-profile partition handles; forbids cross-profile storage path collisions and stale identity/rebind.
- Browser-native CoreWebView2.PermissionRequested side effects deny by default. No consent is ever issued to page code or from an extension/IPC. Popup requests are refused. Navigation synchronously revokes native authority and Rust channel; subsequent authenticated rebind must have new document and generation.
- The bounded run requires two separately hosted real WebView2 profiles and authenticated MV3/Rust channels; checks partition boundaries, stale-channel denial, native navigation retirement and regeneration; packages exact source SHA plus enumerated SHA-256 files, reparse protection and no unlisted artifact files.
- A separate D:-only run-native.ps1 refuses a mismatched checkout or non-empty output. No provider login, credentials, Send, private profiles or user-generated conversation content.

## Deliberately incomplete / non-acceptance

Full physical 8L1 acceptance remains **NOT RUN**. The branch now includes opt-in native same-profile multitab, browser crash, host process relaunch and owner-driven one-use permission scenarios, but none of their interactive side effects has a verified accepted-SHA physical Windows receipt yet. The full *JavaScript* 8B/8C controllers are not invoked as runtime callbacks: this source-owned C# authority implements the exercised host boundaries and accompanying native policy regressions, but broader 8B logical session handoff and real provider sign-in are separate, unimplemented product integrations. Existing Node tests prove the accepted JS contracts, while the dedicated Windows C# self-test proves only native policy decisions. Hosted compilation cannot certify physical crash, permission UX, profile retention, screenshot or performance. Every bounded receipt continues to report `native8L1Accepted=false`. Issue #71, physical 8L1, 7U1 and 15HOST remain blocked pending independently accepted evidence.

## Changes Required repair candidate (2026-10-25)

- Privileged WebView2 `PermissionRequested` now sets `State=Deny` by default and `SavesInProfile=false`; only an actual host-owned modal owner Yes can permit one precise capability, for the current authenticated profile, tab, document, native partition, host generation and origin. Unsupported kinds, arbitrary page messages, foreign origin, stale binding, replay, concurrent dialogs and response uncertainty deny. The host counts actual approvals/denials without storing prompt content or location.
- Native `FreshRebind` now checks profile identity, tab, stable OS partition/path, session, nondecreasing worker generation, increasing navigation/host generation and distinct document; the policy self-test includes positive and multiple negative cases, and is invoked by Windows CI from the compiled product-owned host.
- The bounded native run creates a second actual WebView2 tab in profile A, verifies it shares a native-minted partition with A but not B, verifies Rust denies a competing application-session claim, and requires real disposal/retirement before rebinding A on a new document.
- Native `ProcessFailed` is wired to revoke **all** active WebView2 browser scopes and schedule Rust retirement, not only the reporting tab. Opt-in `-CrashProbe` issues a real browser-process crash and requires WebView2 failure notification plus confirmed Rust retirement of all current scopes.
- Opt-in `-ConsentProbe` requests geolocation from the isolated synthetic page twice. A human must choose Allow once and Deny once in the actual native dialogs; the host checks that the two events were received and no permission was persisted. The probe discards location results. Default runs do not prompt.
- Opt-in `-VerifyRestart` launches two separate fresh OS host/Rust process pairs with exact source and artifact manifests, compares both process IDs and both hashes, and records `restart-receipt.json`. This is a clean process relaunch only; it does not assert persistence of a prior browser profile or completed crash/recovery.

### Exact acceptance boundary and reproduction

Hosted Windows runs C# native policy self-tests, WebView2 compile, SHA manifest and Rust/MV3; Windows+Ubuntu run accepted 8B/8C JavaScript contract regressions and strict Rust checks. A final exact-HEAD CI result is mandatory before merge. Native C# implements a bounded, directly tested **equivalent authority for this synthetic host's exercised paths**, rather than invoking the full 8B/8C JavaScript controllers: it does not implement 8B cross-profile logical session handoff, provider sign-in, or their JavaScript host callbacks. These parts require integration before general product use.

For physical qualification on the accepted merged SHA, the source-matched Windows host can be launched through `probes/8l1/run-native.ps1 -Repo ... -ArtifactRoot ... -Out ... -VerifyRestart -CrashProbe -ConsentProbe` using fresh isolated D: output. The owner must explicitly operate the permission dialogs. Cloud runner compilation and self-tests alone do not establish physical host behavior, browser crash recovery, consent outcomes, or complete 8L1 acceptance. Do not mark 8L1, 7U1, 15HOST or overall performance gates PASS without independent receipts.
