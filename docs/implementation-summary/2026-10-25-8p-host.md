## Native gate implemented

- `apps/windows-host/Native8P.cs` introduces a host-only maximum-16 provider ID + exact HTTPS origin allowlist with explicit, separately configured redirect origins. Canonical origin syntax, duplicate IDs, subdomain impersonation, userinfo, query/fragment credentials, custom schemes, wrong-provider redirect, malformed config and unlisted providers fail closed.
- The isolated product Windows host `--8p --8p-config <D:\...json> --8p-provider <id>` requires a native Yes/No consent (default No), creates a fresh D: WebView2 browser profile, navigates only to the selected provider's bare landing origin and checks each real `NavigationStarting` event. Popups and all permission requests are denied and not saved. A navigation invalidates any prior document authority.
- No renderer/extension argument can configure the allowlist or grant consent. The user must supply the native-owned policy file; CI uses the synthetic inline selftest only.
- The old 8L1 synthetic host remains distinct. The production host now installs the bounded verified MV3 worker in an isolated extension-enabled WebView2 profile, attests exact extension ID/service-worker CDP target, bootstraps fresh Rust 7L2 channel via the source-owned child pipe, and rebinds on each successful allowed document navigation. Native navigation synchronously revokes the previous browser scope and proves Rust retirement before rebind. **No production code invokes `ObserveAsync`, ledger, CDP tool capture, or permissions.** A configured HTTPS origin alone never grants content observation.
- `.github/workflows/8p-host.yml` builds native Windows host/Rust child, executes compiled C# allowlist and synthetic regression suites, runs Rust and JS 8B/8C tests on Windows and Ubuntu, and publishes a source-SHA and all-loadable-binary SHA256 verified Windows bundle. The physical script `probes/8p/run-native.ps1` requires the exact matching D: checkout/artifact and fresh isolated output. No credentials, navigation URLs or account data are added to the receipt.

## Reclaim generation 3 — production native logical handoff and OAuth callback one-use fence

**Scope separation:** All source changes remain in draft PR #124. The native 8P transport-only MV3 worker never reads account DOM, cookies, storage, or executes a browser tool. Its new `attestSession()` signs only the in-memory 7B `DocumentIdentity` with the active non-extractable bootstrap key. Rust `NativeBrowserBridge.observe` verifies the HMAC and installs a first-proof; the purpose is session attribution, not browser content observation.

**8B/8C privileged production handoff path (new opt-in `--8p-handoff-probe`):**
- Creates two **separate** WebView2 OS user-data profiles/environments A/B under fresh isolated D:, each with its own installed zero-permission extension, browser-owned CDP service worker, channel, document and logical app session. Both profiles must reach a verified exact configured provider origin.
- A native default-No confirmation snapshots both WebView2 identities; a reentrant navigation or a changed profile/document/session fails closed. Each worker signs the current identity, and Rust 7B verifies both first-proofs.
- The host retires and confirms **both** prior Rust channels before issuing Rust's atomic `handoff`. C# verifies both still-current native document/profile bindings before committing both local session epochs and only logical attribution. Cookies, storage, profile files, OAuth data and authentication **never** move.
- Repeating the old Rust handoff must fail. Fresh **actual WebView2 navigation** to the provider landing origin (not a fabricated document ID) creates new document, navigation epoch and worker/host generation. Both profiles must acquire fresh channels and signed Rust first-proofs with updated session IDs; failure leaves the task unaccepted.
- The physical runner exposes `-HandoffProbe` and requires `crossProfileHandoffPassed=true` in the source/binary SHA-bound receipt. No owner-run receipt has been presented. Existing accepted JS 8B/8C and new hosted mock/differential, Rust production-origin and compiled C# negative suites are distinct layers; cloud green does **not** prove end-to-end Windows parity or provider authentication.
- Deviation from exact 8B JS callback sequence: native C# commits paired session epochs after Rust transaction and proves changed worker/channel only *after* an actual new-document rebind. Direct JS controller invocation is not claimed. Independent review must accept this native-contract equivalence explicitly.

**OAuth lifecycle (security-first, not token exchange):**
- On a host-authored WebView2 navigation event, a provider-managed PKCE/S256 authorization request is admitted only from an already accepted primary provider origin with exact native-configured callback URI.
- Native `OAuthNavigationGate` remembers only SHA-256 state digest, provider ID, physical profile handle, logical app session ID, callback URI, navigation epoch, and time; it permits at most 16 pending and five-minute TTL, with up to 1024 consumed replay tombstones. Duplicate, foreign profile/session, stale epoch, mismatched callback, expired and replayed state are refused.
- Code-bearing callback URLs are parsed only at WebView2 `NavigationStarting`, consumed **once**, and **always canceled** so their code is not delivered to a page or stored in receipts. On process crash, disallowed navigation or profile invalidation, pending authorization is killed. This implements a fail-closed callback correlation/replay boundary, **not native OAuth client PKCE verifier creation**, authentication, token exchange or sign-in completion. Real provider-specific OAuth flows need separate independent review and 7U1 owner gate.
- C# selftests cover matching, replay, foreign profile/session/provider/URI, stale epoch and TTL, invalid callback keys and unsafe redirect config.
